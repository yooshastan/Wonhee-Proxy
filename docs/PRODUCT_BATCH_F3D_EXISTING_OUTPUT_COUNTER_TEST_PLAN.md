# Wonhee 0.15.18 — Batch F.3d read-only existing OUTPUT counter comparison

**Status: draft/diagnostic only. Batch F owned kill switch stays OFF.** Branch is based on 0.15.17 F.3c after a successful on-device passive capture of one outgoing ICMPv6 Neighbor Solicitation (type 135) with 2 selected WireGuard identities and exact 3-rule routing ownership.

## What the existing evidence actually proves

- A physical Wi-Fi capture observed **one outgoing ICMPv6 Neighbor Solicitation (type 135)**, with capture status 1 parsed/1 captured, 0 header parse errors, and no reported kernel drops.
- Existing IPv4 and IPv6 filter/OUTPUT chains each had six jump/goto entries and ACCEPT default policies when last inspected.
- These two read-only facts do **not** establish that this packet was generated by Android userspace or crossed netfilter's local OUTPUT hook. Neighbor discovery may have kernel origins and other netfilter hooks may be involved.
- A previous active Batch F guard coincided with connectivity loss, but the precise causal path is still unverified. Do not infer Neighbor Solicitation is the cause and do not create broad IPv6 allowances from this observation.

## F.3d implementation

The existing manually consented, bounded 5-second outgoing physical-interface header capture is unchanged. If exactly selected WireGuard kernel identities, ownership ledger/live routing rules and owned-guard OFF preflight all match, F.3d additionally reads:

- `iptables -t filter -n -v -x -L OUTPUT` before and after the capture.
- `ip6tables -t filter -n -v -x -L OUTPUT` before and after the capture.

These commands **only read** existing filter/OUTPUT rule counters. They never insert/delete/flush rules, set policies, zero counters, create new hook points, send packets or change tunnels, routes or DNS. Raw rule addresses, UID selectors, chain names and packet headers remain in ephemeral RAM and never appear in the displayed result or persisted journal.

Each family produces exactly one of: `MOVED`, `NO_MOVEMENT`, `UNAVAILABLE`, `RULE_SET_CHANGED`, or `COUNTER_RESET`. The comparison is valid only if both reads have the same recognized base policy and **identical ordered non-counter rule text**. Counter decreases invalidate the reading; any unrecognized/truncated or inaccessible output becomes unavailable rather than zero.

When comparable, output shows only default-policy packet delta, number of existing OUTPUT rules with rising counters and sum of rule-count increases. **These are not unique packet counts.** The default-policy counter counts only packets reaching default policy, not every packet entering OUTPUT. Per-rule increments may include unrelated apps/flows and multiple rules can be counted for one packet. Physical-interface captures and counter snapshots are not temporally atomic and never establish per-packet correspondence or UID.
