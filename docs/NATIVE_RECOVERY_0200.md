# 0.20.0 — guarded recovery preview
Baseline 0.19.0 (70bef6aebaf979b0d08a87e8b8cfad767da12d0f): device verified 117 authenticated DNS responses, 6 connections opened/closed, 113 reuse attempts (2 fresh retries), 34 ended relay-port rejects, no DNS failures or queue drops, 3 active tunnels. No verified cache hits yet. 
Same package, versionCode 152; no production manifest change. Native JNI invokes VpnService.protect(int) virtually: the app-routing service now requires super.protect plus physical Network.bindSocket on a duplicated descriptor for both native socket families. Bootstrap remains authenticated, pre-capture only. Existing DNS, UID, policy and HOSTS handling stays intact. 
Recovery starts after underlay or peer health loss, or explicit test, while the existing TUN stays established. Close old relay and peer handles, verify cleanup, clear flow ledger, select current validated physical network or another validated Wi-Fi/cellular network, update Android underlying-network metadata, create sessions using the same immutable in-memory resolved profile snapshot, verify all handshakes/protection before new DNS relay and forwarding. Discard traffic during recovery; no direct data fallback. Five attempts with 1/2/4/8/16 second backoff and up to 60s handshake wait per attempt. If unavailable, stop forwarding and hold TUN until Stop. If VPN visibility/consent is lost, report CAPTURE LOST rather than claim protection. Manual guard remains terminal until Stop. Session block count cumulative, DNS generation-specific counters reset when relay replaced. Endpoints are frozen within a session; if endpoint changes, manual Stop/Start is needed. Existing underlay retained while validated; no forced switch just because a second network appears. 
Automatic recovery default on; disable in Protection, applies next Start. Test from Activity on noncritical selected apps. Validate same TUN/network identity, traffic interrupted during recovery, no exposed real IP, renewed app connections, home route, DNS, actual Wi-Fi/cell loss, stop and retry exhaustion. No guarantee before initial establishment, after explicit Stop, revocation or process death. Always-on intentionally remains disabled; cannot safely claim Android lockdown compatibility with selected-app scope. DoQ/DoH3 and virtual TCP DNS fallback remain separate tasks. CI schedule/model and static checks are not on-device recovery verification.
