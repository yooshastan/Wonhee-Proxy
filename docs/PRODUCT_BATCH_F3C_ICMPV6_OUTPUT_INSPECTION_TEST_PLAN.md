# Wonhee 0.15.17 — F.3c passive ICMPv6 subtype and read-only OUTPUT rule inventory

**Draft diagnostic only; Batch F remains OFF.** This work follows successful F.3b.1 sampling (one outgoing ICMPv6 header, unclassified subtype; 2/2 live kernel identities; 3/3 exact split-route ledger; guard OFF/ABSENT) and user-confirmed working HOME/Navidrome and public browsing afterward.

## Narrow purpose

F.3c adds two additional, non-enforcing observations to the existing user-consented passive physical-underlay packet-header sample:

1. Categorize any outgoing **ICMPv6 candidate** explicitly reported by the text of tcpdump into router solicitation (type 133), router advertisement (134), neighbor solicitation (135), neighbor advertisement (136), redirect (137), echo request/reply, other known errors, or **UNKNOWN**. Never infer a subtype from IPv6 multicast addresses or packet direction. If tcpdump does not print a recognizable subtype, report UNKNOWN rather than make a guess.
2. Read the **existing** IPv4 and IPv6 local `OUTPUT` rule listings with `iptables -S OUTPUT` and `ip6tables -S OUTPUT`, separately. Only summarize the number of OUTPUT rule entries and jump/goto entries, and a recognized default policy if available. Do **not** show any rule text, address, owner UID, chain name or endpoint.

These are **two parallel observations**; neither connects a captured packet to a netfilter rule. The rule inventory is not a packet counter, nor is it evidence that Android's own control-plane used OUTPUT. Neither observation proves packet origin, UID, socket provenance, rule reachability, actual traffic delivery, a leak, or the safety of re-enabling the experimental kill switch.

## Unchanged safety conditions

- The original F.3b/F.3b.1 root preflight still requires exactly selected and verified HOME/AirVPN WireGuard identities, split-route ledger/live exact match, Batch F guard ownership OFF and no owned live IPv4/IPv6 anchor/chain.
- Only after manual consent: bounded **5-second, outgoing-only**, max **32** matching packet headers, 64-byte snap length, physical underlay (wlan0/rmnet16 candidate), no pcap file, raw output retained only in transient memory.
- Root `tcpdump` and `timeout` required; absence causes refusal.
- No network-generated probe, DNS query, firewall/route writes, netfilter rule insertion, counter insertion, implicit connection changes or automatic fallback. Device firewall guard activation and packet challenge remain disabled.
- No raw packet headers, peer keys, IP addresses, UID selectors, shell output or netfilter rules are written to persistent logs/journal or displayed. Aggregates only.

## Regression tests and release gate

Pure Java `RootF3cEvidenceTest` covers known ICMPv6 types, unknown/missing subtype, aggregate count redaction and OUTPUT listing parsing with raw data hidden. Existing `RootUnderlayControlEvidenceTest` remains in CI. Android debug APK compilation and independent native WireGuard tests must pass on the final branch commit before distributing the build.

## What F.3c does not solve

A physical-interface outgoing ICMPv6 message could be generated by the kernel, Android, or another component; this small capture does not establish which. Even read-only `iptables -S OUTPUT` only enumerates chain rules, not packet-traversal or conntrack observations. **Do not create broad ICMPv6 or underlay exceptions from these summaries.** Design a separate least-privilege OUTPUT-hook attribution experiment that is non-disruptive, with independent USB ADB/root recovery validation before any future live guard experiments.
